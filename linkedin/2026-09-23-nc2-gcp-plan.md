## Post (feed)

Nutanix Cloud Clusters on Google Cloud is generally available, and the whole path is code: Pulumi for the landing zone, one call to POST /clusters/gcp on the NC2 v2 API for the cluster, and the Prism Central v4 API for everything above that line. The console never has to be clicked, same as the Azure post.

Three things that surprised me writing it up from the deployment guide rather than the launch blogs.

Six supported instance types, not three, and they split into two storage architectures. Z3 and C4 metal put AOS on the node's own Titanium NVMe. C3 metal has no local storage at all and runs on Hyperdisk Balanced, which decouples capacity from the node and brings its own rules: no resizing from the Google Cloud console, no adding disks to an existing node, and a single volume failure replaces the whole node.

Twenty-three regions, but availability is per instance type rather than per region. Only us-central1, europe-west4 and asia-southeast1 carry all six. Pick the region for the instance, not the other way round.

Flow Virtual Networking is mandatory here, with no VLAN option, and it is lighter than on Azure: no Flow Gateway VMs, which removes a VNet, two VMs and the BGP plumbing.

One more that matters for cost models: hibernate and resume are not supported on Google Cloud. If your AWS plan assumed parking a cluster overnight, it does not port.

## Article

**Title:** NC2 on Google Cloud, as code: Pulumi for the landing zone, the NC2 v2 API for the cluster, the v4 API for everything above

**Cover image:** gcp-plan-01-map.png

NC2 on Google Cloud is generally available, and the whole path is code. Google Cloud lands closer to the Azure post in this series than the AWS one: everything the NC2 console does here, the v2 API also does, including creating the cluster. Full detail and every code block: https://cloudlabworks.dev/nutanix/nc2-gcp-plan-pulumi-v4-api-only

**The whole path, as code**

[image: gcp-plan-01-map.png]

Google Cloud lands closer to the Azure post than the AWS one. Everything the NC2 console does here, the v2 API also does, including creating the cluster, so the mouse comes out of the loop entirely.

**Six instance types, two storage architectures**

[image: gcp-plan-02-substrate.png]

AHV runs directly on Compute Engine bare metal instances, in your own project and VPC, explicitly distinct from Google Bare Metal Solution which is not supported. The first real design decision has no equivalent on AWS or Azure: Z3 and C4 metal carry local Titanium NVMe for AOS storage, while C3 metal has no local storage and uses Hyperdisk Balanced at 15 to 120 TB per host. The C3 path decouples capacity from the node and costs you flexibility in return, since you cannot resize volumes from the Google Cloud console, cannot add disks to an existing node, and lose the whole node when one volume fails.

On the memory column: Google's GA blog lists the two C4 rows the other way round from both Compute Engine's machine-type docs and the Nutanix portal. Two vendor sources against one blog, and only one reading where "standard" and "highmem" mean what they say.

**The landing zone, in Pulumi**

[image: gcp-plan-03-landingzone.png]

Documented minimums: a /24 cluster subnet with the Prism Central /28 carved out of it, and /27 for each of the two Flow Virtual Networking subnets. Three requirements sit outside the resource graph and break deployments quietly: the VPC needs an MTU of at least 2,000 bytes, the Restrict VM IP Forwarding organization policy must not be in force, and compute.trustedImageProjects must not block nc2-mcm-img-mgmt-prod, which is where the AHV, CVM and Prism Central images come from. A bring-your-own Cloud NAT gateway has to be switched from static to dynamic port allocation.

Five ranges are reserved and must not appear anywhere: 192.168.5.0/24, 10.100.0.0/16, 10.200.32.0/24, 10.200.0.0/22 and 100.64.1.0/24.

**Flow Virtual Networking, mandatory, and lighter than Azure**

[image: gcp-plan-04-flow.png]

There is no VLAN-type networking option on Google Cloud. Every user VM sits on a Flow overlay subnet with Prism Central as the control plane and Geneve between hosts. The good news against the Azure post: no Flow Gateway VMs are required here. The constraint to design around: the network your VMs see is not the Google Cloud network, so reaching BigQuery or GKE goes through the overlay's NAT path with floating IPs, or through Private Google Access, Private Service Access or Private Service Connect.

**One v2 call, then v4 only**

[image: gcp-plan-05-apiline.png]

POST /clusters/gcp takes the VPC and subnet names Pulumi just exported, creates the cluster and Prism Central, and returns a task to poll. Above that line, every Flow VPC, subnet, image and VM is a v4 resource under Pulumi, bridged from the official Nutanix Terraform provider, with the same ETag-based safety the AWS and Azure posts rely on.

**Limits that differ from the other two clouds**

Hibernate and resume are not supported on Google Cloud, which breaks any cost model that assumed parking a cluster overnight. Clusters run three to twenty-eight nodes, with two-node clusters unsupported. No IPv6, no Prism Central backup to Google Cloud Storage, and no cross-registration between an on-premises Prism Element and an NC2 Prism Central.

Sources: the portal's NC2 on Google Cloud Deployment and User Guide (Planning, Supported Bare-metal Instances, Supported Regions, Requirements, Limitations, dated 2026-08-25), the Nutanix Cloud Bible at PC and AOS 7.3.1.1, the NC2 v2 API reference, and Compute Engine machine-type documentation.
