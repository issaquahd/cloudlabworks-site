## Post (feed)

Nutanix Cloud Clusters on Google Cloud is generally available, and it is the same product you already run on AWS and Azure: the NC2 console provisions the cluster, Prism Central runs day two, and the Nutanix stack on the nodes is the stack from your data center.

What is genuinely different is underneath and in the middle. Underneath: Google Compute Engine bare metal instances, C4 and Z3 with `-metal` in the machine type, in your own project and VPC. Not VMs, not nested virtualization, not Bare Metal Solution. In the middle: Flow Virtual Networking is mandatory there, not optional the way it is on AWS and Azure, so the network your VMs see is the overlay and not the Google Cloud network. That is the one place the AWS muscle memory does not transfer.

Third in the series, same terms as the first two: Pulumi for the landing zone this time instead of Bicep or OpenTofu, and once Prism Central answers, only the v4 API touches it.

One receipt from the writing. Google's own GA announcement lists the memory for the two C4 bare metal types backwards against the Compute Engine machine-type docs. If you size from the blog post, you size backwards. The docs are right.

## Article

**Title:** NC2 on Google Cloud, as code: the console builds the cluster, Pulumi and the v4 API do the rest

**Cover image:** gcp-plan-01-map.png

Two posts this week walked NC2 on AWS and NC2 on Azure exactly as the public deployment guides describe them. Google Cloud gets the same walk, because it is the same product, generally available, provisioned by the same NC2 console. The constraints handed to the lab for this one: Pulumi as the infrastructure-as-code tool instead of Bicep or OpenTofu, and once Prism Central answers on 9440, only the v4 API touches it. Full detail, every code block, and the correction this post carries at the top: https://cloudlabworks.dev/nutanix/nc2-gcp-plan-pulumi-v4-api-only

**Who does what**

[image: gcp-plan-01-map.png]

The NC2 console obtains the bare-metal instances, sets the IAM it needs, writes the VPC firewall rules, watches the hardware and replaces failed nodes. Your project and your VPC hold everything else. Prism Central is what you talk to, and from there the v4 API is the only interface this post uses.

**The substrate: GCE bare metal**

[image: gcp-plan-02-substrate.png]

AHV runs directly on Compute Engine bare metal instances, ordinary GCE instances with `-metal` in the machine type, distinct from Google Bare Metal Solution. Workload storage is the node's local Titanium SSD, claimed by the CVM for AOS. Three qualified machine types at GA, and a note worth the re-check: Google's own GA blog swaps the memory figures on the two C4 rows against the Compute Engine documentation. The docs are right, and they are also the only reading where "standard" and "highmem" mean what they say.

**The landing zone, in Pulumi**

[image: gcp-plan-03-landingzone.png]

You can let the console create the VPC for you. This series does not, because the network is code you own. That means the Prism Central /29, the Flow NAT range as a secondary range, and the no-NAT subnet all have to exist before the console asks for them. Five CIDR blocks are reserved for AHV-to-CVM traffic, the VTEP subnet and CSMP, and using one of them does not fail at `pulumi up`, it fails an hour into a cluster build.

**Flow Virtual Networking is mandatory here**

[image: gcp-plan-04-flow.png]

On AWS and Azure, Flow is a choice. On Google Cloud there is no VLAN-type networking at all, so every user VM lives on a Flow overlay subnet with Prism Central as the control plane, and reaching BigQuery or GKE from a VM goes out through the transit VPC or over Private Google Access, Private Service Access or Private Service Connect.

**The line: v4 API only**

[image: gcp-plan-05-apiline.png]

Below the line the console builds the cluster. Above it, every Flow VPC, subnet, image and VM is a v4 resource under Pulumi, bridged from the official Nutanix Terraform provider (`pulumi package add terraform-provider nutanix/nutanix`), with the same ETag-based safety against a colleague's console click that the AWS and Azure posts rely on.

**What is verified, and what is not**

- Verified against vendor documentation: GA status and the seventeen-region starting footprint, GCE bare metal as the substrate, the three machine types and their specs, the console as the provisioning control plane, the two service accounts, mandatory Flow Virtual Networking, the network layout, node placement across Availability Domains, license portability.
- UNKNOWN, and marked as such rather than guessed: whether the NC2 v2 API has a create-cluster endpoint for Google Cloud the way it does for AWS and Azure. The reference renders client-side and its worked example is the AWS one. If it exists, the console step collapses into one more API call.
- Corroborative only: the reserved CIDR list, which comes from a community landing-zone repository rather than the guide's own text.
